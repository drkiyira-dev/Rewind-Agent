# 恢复契约 v0.1

本契约约束 `rewindagent` 原型。它不是通用 Agent 运行时的规格。

## 1. 支持与不支持

支持：

- 单次解释、有限步、纯函数工具。
- 受控内存槽位。工具只能通过 `State.observe` / `State.write` 接触状态。
- 固定步，或由纯槽位决定的 `if`，或行程不超过 4 的 `for`。
- 一次已知故障：错误输出。故障身份由场景给出，不做归因。
- 工具实现号或配置变化引起的缓存失效。
- 一条模拟的不可逆投递账本。账本不是槽位。

不支持，必须拒绝或停住，不能算恢复成功：

- 行程超过 4，或无法从受控槽位得到行程。
- `escapes=True` 的工具。选择性恢复直接拒绝。
- 需要发送与已入账不同的新载荷。不补偿、不撤销旧账。
- 持续故障。只重算一次，然后 `persistent_fault`。
- 多 Agent、模型调用、真实网络、真实数据库、补偿引擎。
- 任意 Python 隐藏依赖。原型看不见，也不声称看见。

## 2. 故障模型

| 种类 | 条件 | 行为 |
|---|---|---|
| 一次性错误输出 `removed` | 恢复开始前，该实例改回契约工具。坏输出只存在于原轨迹和缓存 | 该实例不得命中旧缓存。下游只按新的输入值哈希决定 |
| 持续故障 `persistent` | 契约工具没有换回来 | 该实例重算一次。输出哈希仍等于记录的坏哈希则停止，状态为 `persistent_fault` |
| 未声明但被 API 看见的读 | 工具读了不在本次 `reads` 里的槽 | 禁止该实例缓存命中，必须重算 |
| 不可观察逃逸 | `escapes=True` | 拒绝选择性恢复 |
| 状态槽损坏 | 不单独模拟。错误写入用错误输出来表示 | 读者通过生产者和值哈希失效 |
| 日志或检查点损坏 | 哈希链或内容哈希不符 | 装载失败，不继续 |

所有基线面对同一故障模式、同一初始槽位、同一已入账效果。`removed` 场景下大家都使用修好的工具。`persistent` 场景下大家都不使用修好的工具。

## 3. 恢复开始时故障是否已经消除

由场景字段 `fault_mode` 固定。

- `removed`：已经消除。
- `persistent`：没有消除。
- 无故障的实现/配置变化：没有步骤故障，缓存键里的实现号或配置变了。

不在运行中偷偷改变这个字段。

## 4. 身份、版本、生产者、控制与效果

- 事件实例：`step_id`，循环体为 `step_id#i`。同一步的两次执行不是同一个实例。
- 槽位版本：分支内单调整数。跨分支比较不用版本号，用值哈希和生产者实例。
- 初始值：生产者 `genesis`，版本 0。
- 环境在恢复前改写的槽：生产者 `environment`。这不是缓存的隐式输入，除非工具后来通过 API 读到它。
- 数据依赖：这次 `observe` 实际返回的那个生产者。一个写者的每个读者各有一条边。
- 写后写、以及“写了但没读前值”的覆盖：只记 `order_ww`，不进入失效闭包。
- 读后写：若本次读过该槽再写它，数据边来自那次读；同时记一条 RMW 提交约束。
- 控制读：`control_bool` / `control_int` 产生控制事件，读边指向被读槽的生产者。
- 效果记录：账本条目 `(logical_id, payload_hash)`。`logical_id` 用步骤实例，不用 run_id。

规范化哈希覆盖工具实现号、配置、输入值、输出值和账本载荷。不覆盖 run_id、墙钟、进程号。布尔值不当成整数处理。

## 5. 缓存失效

缓存键是：

`实例身份 + 实现号 + 配置哈希 + 按声明顺序排列的输入值哈希`

任一变化都是未命中。另外即使键相同，下列情况也不命中：

- 该实例是本次故障实例。
- 原条目带有未声明读违规。
- 原条目的工具 `escapes`。
- B4 正在处理不可逆步骤：不走纯计算缓存，走账本规则。

值哈希相同只在该工具的契约等于“规范化值相等”时表示输出可以沿用。v0.1 的纯整数/布尔工具采用这个契约。不外推到未声明契约的工具。

## 6. 集合

这些集合不互相替代：

- **受影响闭包**：从故障实例沿数据边和控制边反向传递。包含全部读者，不是第一读者。这是保守说明，不是最优集。
- **重算**：这次解释里真正调用了工具的实例。
- **复用**：纯计算缓存命中，或不可逆步骤确认账本已有相同载荷因而未再投递。
- **前缀跳过**：只有 B1/B2。来自快照，不是 B4 的复用。
- **废弃**：原轨迹有、这次解释没再走到的实例。它们的旧写入不得进入新状态。
- **新事件**：这次走到、原轨迹没有的实例。
- **阻塞 / 拒绝**：未恢复成功。不计入恢复成功分子。

B4 不承诺这些集合全局最小。

## 7. 状态重建、冲突、计划失效

B4：

1. 新建分支状态，只放入 `genesis` 初始值。
2. 如场景声明了恢复前环境改写，再写那些槽。
3. 重新执行工作流函数。
4. 缓存命中才把旧输出写到当前槽。写之前检查：RMW 的当前值哈希必须等于当初读到的哈希。不等则 `Conflict`，槽位保持原样，状态变为 `write_conflict`。
5. 没走到的旧实例不写任何槽。

禁止用整份历史状态覆盖当前分支来实现 B4。

若重算改变了分支条件，解释器走新分支。旧分支实例成为废弃。不执行一份已经失效的事件列表。

## 8. 拒绝与停止

必须拒绝或停止，且成功标志为假：

- 行程超过上界。
- 存在 `escapes` 工具。
- 恢复将产生新的逻辑投递，或改变已投递载荷。
- 检查点或日志哈希失败。
- 持续故障一次重算后输出仍是坏哈希。
- 验证器发现复用集读了受影响生产者，且输入值哈希已经不同。
- 写入冲突。

v0.1 没有人工工单系统。拒绝的状态字符串就是升级记录。

## 9. 正确性承诺与假设

在下列假设同时成立时，B4 的目标是：若状态为 `recovered`，则受控槽位与“无故障、从 genesis 解释一次”的结果一致，且账本不增不改。

假设：

- 工具除返回值外不修改受控状态，隐藏读只通过本原型的 API。
- 纯工具由声明的输入值决定输出。
- 工作流在上界内是确定的。
- 故障模式字段诚实。
- 没有 B4 以外的代码改账本。

不承诺：

- 全局最小重算。
- 任意 Python 程序。
- 已发出消息可以被撤销。
- 测试没覆盖到的工作流。
- 形式化证明。当前测试通过只说明这些测试没有失败。

## 10. 损坏与失败

- 日志：每行含 `schema_version`、`prev`、`body`、`hash`。任一环不上就 `LogCorrupt`，不跳过坏行。
- 检查点：内容哈希不符就失败。B1 不得使用它。B4 本来不读取业务检查点。
- 补偿：没有补偿器。补偿失败这一情况在 v0.1 不发生，因为不执行补偿。不可逆效果失败时的状态是“旧回执还在，恢复没有发布新槽位”。
- 拒绝发生在新的外部提交之前。恢复把槽写在候选状态里。只有状态为 `recovered` 时，候选槽才复制到 `published_values`。拒绝、失败和结果未知都不发布；`candidate_values` 只留作诊断，调用方不能把它当成正式结果。
- 丢弃候选状态不会清空外部效果台账或本地回执。内部隔离不是外部事务回滚。
- 恢复尝试不就地修改调用方持有的原运行记录、缓存对象或检查点对象。下一次尝试从原记录重新开始，不从上一份未发布的候选状态继续。
