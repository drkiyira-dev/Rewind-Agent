## 相对普通增量执行，多解决了什么

Skyframe 已有的机制（文档原文，不是本项目的发明）：

- 节点只能通过已登记依赖读取输入。未登记的读会让增量构建出错。
- 失效集是变更输入的反向传递闭包。Bazel 做的是自底向上失效。
- change pruning：重建后值没变，则曾因它而失效的下游可以恢复。
- 失效是整节点重算，不是在旧值上打补丁。
- 图在求值完成后是 DAG。依赖可以分多轮才发现。

因此，若 RewindAgent 只做“版本化输入 + 依赖失效 + 缓存复用”，它就是把 Skyframe / Make / 构建系统的已知机制套到 Agent 步骤上。这可以有工程集成价值，但不是研究创新，也不该叫新算法。

本轮原型额外要检验的，只是构建系统通常不负责的三件事：

1. 已经发生的外部效果放在另一本书上，内部状态重建不能删掉它，也不能因为缓存命中就再发送一次。
2. 受控接口看见了未声明读时，禁止复用该缓存；工具被标记为可能逃逸受控接口时，拒绝选择性恢复，而不是假装能圈定影响范围。
3. 运行时检查不能读取评测答案。全量重跑也要经过同一本外部效果账，不能靠清空账本来变正确。

这三件事是否构成值得长期做的研究，要看实验结果。在纯计算图上如果和普通增量没有差异，结论就写没有差异。

## 问题清单

### P0-1 数据依赖不能只连到“写之后的第一次读”

- 报告说法：数据边连接某槽位的写和之后第一次读，中间不能有另一次写。
- 反例：E1 写 `x`，E2 读 `x` 产生 `a`，E3 读 `x` 产生 `b`。只失效 E2 会把 E3 留在脏缓存里。
- 风险：错误复用。级别 P0。
- 修订：每一次读都记录实际看见的 `(slot, version, producer, value_hash)`。初始值的生产者是 `genesis`。失效沿所有读边的反向传递闭包走，不取“第一读者”。
- 阻断：阻断旧规格。不阻断按本修订实现的原型。测试 `test_multi_reader` 与 `test_contaminates_all_readers`。

### P0-2 同槽多次写入不是一条数据边

- 报告说法：写和之后的读之间不能再有写，容易把写后写、写后读收成同一种边。
- 反例：E1 写 `x`，R1 读这个版本，E3 不读 `x` 直接覆盖 `x`，R2 读 E3 的版本。E1 出错时 R1 必须重算；E3 和 R2 的输入值没有变，不应只因为槽位同名就被失效。
- 风险：该复用的不复用，或反过来把旧版本的读者漏掉。级别 P0。
- 修订：数据依赖是“这次读到的那个版本的生产者”。写后写、读后写只记提交顺序，不进入失效闭包，除非后写确实读了前写。
- 阻断：不阻断修订后的原型。测试 `test_multi_version`。

### P0-3 动态事件轨迹上不要为了循环去造 SCC

- 报告说法：静态计划里的环用强连通分量整块重算；动态事件图同时又按时间全序连边。
- 反例：展开后的循环迭代只产生从较早实例到较晚实例的边。这个图没有环。把多次迭代收成一个 SCC，会把已经不需要重算的迭代绑在一起，或者在修复后行程变化时继续执行旧事件列表。
- 风险：复用已失效路径上的写入。级别 P0。
- 修订：区分静态循环、一次运行展开出的事件实例、迭代之间的槽位版本。实例身份是 `step_id#迭代号`，不是工具名。选择性恢复从初始状态重新解释工作流；没再走到的旧事件标为废弃，其写入不会落地。行程或分支若超出声明上界，拒绝，不沿旧列表继续。
- 阻断：不阻断。v0.1 支持有上界的展开，不支持任意动态控制。测试 `test_loop_unfolded`、`test_control_abandons_old_branch`、`test_unbounded_refused`。

### P0-4 未声明读没有自动全知

- 报告说法：未声明读要保守扩大，但没说明观察边界。
- 反例：普通 Python 可以不经过状态对象去读全局变量、文件或时钟。系统看不见，就没有“扩大到这里为止”的边界。
- 风险：把包装器说成沙箱，从而错误复用。级别 P0。
- 修订：只承认受控 `State` API 上的读。声明读与实际读不一致：禁止缓存命中，必须重算。工具标记 `escapes=True`：拒绝选择性恢复。不声称能分析任意函数。
- 阻断：不阻断受控模拟器。测试 `test_undeclared_read_not_reused`、`test_escape_refuses`。

### P0-5 复用不是跳过，也不是把旧状态对象抄回来

- 报告说法：可复用节点的结果可以沿用，但没定义这些写入如何进入新分支，也没禁止整份状态复制。
- 反例：把故障之后的快照整份拷回，会把脏的 `x` 一起拷回；随后只跳过一个节点，脏值仍在。
- 风险：状态污染。级别 P0。
- 修订：B4 从 `genesis` 重新解释。旧结果进入新分支的唯一途径是缓存命中，并且命中条件是实例、实现、配置和输入值哈希一起匹配。落地时若声明了基版本而当前值不同，写入函数在修改前抛出冲突。B1/B2 才会恢复前缀快照，它们是基线，不是 B4。
- 输入版本身份、值哈希相同、语义等价是三件事。v0.1 只在工具契约写明 `equivalence=canonical_value` 时，把规范化值哈希当作相等。不把哈希当作任意工具的语义证明。
- 阻断：不阻断。测试 `test_write_conflict_does_not_clobber`、`test_b4_does_not_restore_checkpoint`。

### P0-6 幂等、补偿、可逆、正确性不能混用；全量重跑不能绕过账本

- 报告说法：效果类别里有 idempotent，全量重跑是安全兜底。
- 反例：幂等读仍可能读到已经变化的外部值。幂等写可能覆盖后来的合法更新。补偿通常是一笔抵消业务，不是把世界还原。内部快照回滚不能让“消息已发送”消失。故障已经把消息发出去之后，再重跑发送会尝试第二次效果。
- 风险：重复外部效果或伪称撤销。级别 P0。
- 修订：v0.1 不做补偿引擎。外部账本只追加。恢复开始时账本里已有的投递保持不变。载荷相同的再次投递被账本抑制，不计为成功的干净恢复。载荷不同则拒绝写入，并拒绝把这次恢复叫成功。B4 在载荷将变时不调用投递。B0 也使用同一账本，不许清空。
- 阻断：不阻断模拟账本。测试 `test_ledger_survives_state_restore`、`test_irreversible_same_payload`、`test_irreversible_changed_payload`。

### P0-7 验证器不能看见评测答案

- 报告说法：确定性工具的重算输出与预言机一致，放在验证器里。
- 反例：预言机就是无故障的最终状态。规划器若能读到它，可以按答案挑选复用集合，测试会一起变绿。
- 风险：虚假正确性。级别 P0。
- 修订：`verify.py` 只看轨迹、版本、契约和账本。`evaluate.py` 里的对照值由测试自己按步骤公式计算，或由一次不调用规划器的干净解释计算。两边允许使用同一批纯函数的数学定义，但手写案例另有期望字典。
- 阻断：不阻断。测试 `test_bad_plan_rejected` 不导入评测期望。

### P0-8 持续故障不能靠停机假装成功

- 报告说法：策略可以在几种恢复里挑选，但没写故障是否已经移除。
- 反例：工具仍返回错误值时反复重试，或重试一次后把停机报告成恢复成功。
- 风险：虚假成功。级别 P0。
- 修订：`removed` 与 `persistent` 是两种已声明条件，所有基线相同。persistent 只重算该实例一次；输出哈希仍等于已记录的坏哈希则状态为 `persistent_fault`，不进入成功。
- 阻断：不阻断。测试 `test_persistent_fault_stops_once`。

### P1-1 “最小”没有证明

- 报告说法：输出最小必要恢复范围，算法名也像全局最优。
- 证据：Skyframe 自己也只保证失效闭包，change pruning 之后的集合才较小，且文档写明这不是任意增量算法的最优。动态控制下的全局最小恢复在本轮没有证明。
- 风险：性能结论夸大。级别 P1。
- 修订：对外只说“契约内的保守选择性恢复”。仅在一个 5 节点纯图上，用测试里独立枚举的可行子集做对照。该对照不推广。
- 阻断：不阻断原型。阻断任何“已证明最小”的写法。

### P1-2 纯计算上的收益可能只是普通增量

- 报告说法：依赖感知恢复应少于后缀重跑，并可能少于最近检查点。
- 推断：菱形图里，故障点之后仍有一条独立支。后缀重跑会重算它，输入哈希缓存不会。这是 Skyframe 已覆盖的差异。B4 若与 B3 计数相同，不能写成新算法胜利。
- 风险：基线不公平或事后改指标。级别 P1。
- 修订：评测方案预先写明 B0–B4，并写明“纯计算上 B4 与 B3 相同”是可接受的如实结果。安全门禁不看谁比不安全基线更好。
- 阻断：不阻断。若实现把 B3 做成故意更弱的稻草人，则阻断；本原型不那么做。

### P1-3 上一份报告对相邻项目的覆盖声明过宽

- 证据：本轮确实看到 VCR 恢复器、Bisect 归因、LangGraph 后缀重跑、Crab README 的沙箱检查点是不同问题。但是 agent-replay 未逐文件审，论文实现是否开源 **Unverified**，Skyframe 已覆盖纯增量部分。
