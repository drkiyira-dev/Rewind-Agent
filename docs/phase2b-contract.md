# 第二阶段 B 契约（实验前写定）

本文件在外部效果实验之前写定。允许的结果是集合。实现不得在看到结果后把未知改成成功，或把禁止的重发改成允许。

这不是新的恢复规划算法。进程内 `choose_action` 在查询结果为 absent 时会发送；那个规则不用于本阶段。没有回执不能推出没有执行。查询“当前未找到”也不能推出可以重新提交。

本轮没有重新打开 Stripe、AWS 和 LangGraph 的在线文档（环境拦截了这些请求）。下面的规则只属于本项目。借用的概念仅是：同键同载荷可以去重、同键异载荷是冲突、幂等保留期限有限、结果未知不等于失败。

## 三个存储

- 工作库：任务、步骤、效果身份、发送尝试、已采纳回执。
- 服务库：业务追加记录和幂等记录。只有模拟服务进程打开它。
- 运行状态：本次进程的锁和内存。进程退出后消失。

工作进程只能访问自己的工作库、受信任登记表，以及服务的 `GET /v1/capabilities`、`POST /v1/effects`、`GET /v1/effects/<key>`。它不能得到服务库路径、故障点、预期值或生效计数。

测试器可以读两份库来评分。这不是操作系统沙箱。

## 身份

逻辑操作身份由工作流里的 `logical_id` 固定，resume 不重新生成。

幂等键在首次进入 PREPARED 时计算一次并保存：

`semantic_hash({service_id, contract_version, caller_scope: run_id, logical_id})`

键不包含载荷摘要。跨 run 不去重：新的 run_id 是新的调用方范围，同名步骤不自动代表同一次业务操作。

发送尝试号每次可以不同，但不能代替逻辑身份。两个逻辑身份即使载荷相同也是两次操作。同一逻辑身份出现不同载荷则拒绝。

服务身份或契约版本与已保存的不一致时停止，不改投另一个服务。数据库里的字符串不能决定 URL、模块或命令。

## 状态

| 状态 | 含义 | 能否 POST |
|---|---|---|
| PREPARED | 身份、载荷和契约已提交，还没有允许发送的尝试 | 仅 resume 的首次提交可以 |
| MAY_HAVE_EXECUTED | 发送尝试已提交。请求可能没发出、正在传输、正在执行，或已经成功但回执丢失 | 不能因为没有完成标志就认定没执行 |
| CONFIRMED | 回执或查询与身份、载荷摘要、服务身份一致，并已写入本地 | 不再 POST |
| REJECTED | 明确冲突或不匹配 | 不再 POST，任务不发布 |
| UNKNOWN | 证据不够 | 不能 POST。以后可以只做核对 |

UNKNOWN 不是成功，也不是阶段 A 那种“失败提交后永远不再处理”。`execution_failure` 仍表示纯计算失败已确定，不再跑那个纯函数。两者不能共用终止规则。

整个任务只有后续纯计算也完成才发布。效果已确认不等于任务成功。其后的纯计算失败不撤销服务端记录，本地也不把它说成外部回滚。

## 服务契约 append.v1

只有 `local-append`、契约版本 `append.v1`。四种公开配置：

| 配置 | 幂等提交 | 状态查询 |
|---|---|---|
| P0 | 是 | 是 |
| P1 | 是 | 否 |
| P2 | 否 | 是 |
| P3 | 否 | 否 |

幂等配置把键、载荷校验、业务记录和可复用结果放在同一个服务端事务里。不支持幂等的配置没有唯一约束，重复 POST 可以产生两条记录。

查询结果只有：`confirmed`、`not_found`、`unavailable`，以及身份或载荷对不上的不可信回执。本服务不提供单独的“处理中”记录；事务未提交时，其他连接看到的是 `not_found`。因此 `not_found` 不授权提交。

幂等保留期限由 capabilities 公布，客户端用自己保存的 `prepared_at_ms` 加这个期限判断，重启不会把这个时间改成现在。超期后可以查询并采纳仍然匹配的成功证据，但不能用新键重发。服务进程没有按期限删除去重记录的实现；已验证的是客户端期限守卫，不是服务端过期清理全链路。

## 动作

- `resume`：可以按上面的表首次提交，或在幂等、未超期、且查询没有给出 `not_found` 时用原键再请求一次。查询不可用且没有幂等依据时保持 UNKNOWN。
- `reconcile`：只查询和采纳，不 POST。
- `inspect`：只读工作库，不访问服务。

查询到匹配的 `confirmed` 时只写本地回执，不再 POST。每次调用最多 1 次业务 POST 和 2 次查询。发送尝试计数保存在工作库里，重启不清零。超过 3 次尝试后不再 POST。

## 允许结果

标准混合任务的输入是 `{"n": 2}`。发布值只允许 `n=2`、`n2=3`、`ack` 为 `semantic_hash({"values": [3]})`、`report=4`。

| 窗口 | 允许的结果 |
|---|---|
| E0 身份未提交 | 杀死前服务没有业务 POST。之后的 resume 用原 logical_id 首次提交并可以完成 |
| E1 PREPARED 已提交 | 首次 POST 使用已保存的键，不新造逻辑身份 |
| E2 尝试已登记但请求未必发出 | 无幂等且无查询时必须 UNKNOWN，不能根据测试真值补发 |
| E3 服务已收到但事务未提交 | 查询 `not_found` 时不 POST。旧请求随后可以成功，生效数仍是 1 |
| E4 效果已提交、响应丢失 | 有查询则核对；仅有有效幂等则原键重试一次；都没有则 UNKNOWN |
| E5 收到响应但本地未保存 | 与持久视图相同，只按查询或幂等契约继续 |
| E6 本地确认事务提交前 | 不留下半条回执，不发布候选值 |
| E7 效果步骤已提交、后续纯计算未做 | 只继续纯计算，生效数不增加 |
| E8 已发布但未打印 | 同一发布身份，生效数不增加 |

另外：同身份同载荷不增加生效数；同身份异载荷拒绝且不产生第二条；不同身份相同载荷各生效一次；查询先不可用则 UNKNOWN，恢复后 reconcile 确认且不 POST；UNKNOWN 跨进程保持且不每次 POST；保留期限已过则不重试；锁竞争者没有业务 POST；错误回执不发布；后续纯计算失败则任务失败但效果保留；服务在提交前被杀则重启后没有那条效果；服务在提交后、响应前被杀则效果和幂等记录仍在。

安全完成、合理 UNKNOWN、明确拒绝和执行失败都保留在记录里。UNKNOWN 不是缺陷，除非本表要求的是完成。不安全重发和错误发布算失败。

服务端去重造成的单次生效归属于服务契约，不是客户端单独创造的 exactly-once。本轮不保证断电、任意网络故障或任意第三方 API。

## 本轮接管说明（不修改上面的预先定义）

P2 的 `effects.idempotency_key` 用于查询关联，没有该列的唯一索引，也不在 POST 路径检查已有键。独立新建的 P2 服务库中，直接发送两个相同身份、相同载荷的 HTTP POST，会产生两个不同 `effect_id`，真实生效数为 2。旧验收中的 `dedup_rows` 实际是 `effects WHERE idempotency_key IS NOT NULL` 的计数；新验收改称 `keyed_effect_rows`。旧证据保持原字节。

每个服务库按同一 profile 启动和重启；没有验证在同一库上切换 profile。查询暂时未找到时客户端不再 POST，旧请求完成后可以查询确认，这一 P2 场景与直接重复 POST 的服务端非幂等验证分别保留。
